Features

What TK-Boost Does

NL2SQL agents know how to write SQL. What they lack is experience using real databases. TK-Boost fills that gap.

🧠

Tribal Knowledge

Learns reusable corrective rules from agent mistakes—like a human analyst building intuition over time.

🔌

Bolt-On Framework

Works with any NL2SQL agent. No retraining, no architecture changes—just plug it in.

🎯

CTE-Level Correction

Applies knowledge one CTE at a time for precise, targeted fixes on complex queries.

🔍

SQL-Based Retrieval

Retrieves knowledge from the SQL draft (not the NL query) using structured applicability conditions.

📈

Multi-Benchmark

Validated on Spider 2.0 and BIRD across SQLite, Snowflake, and BigQuery.

⚡

Parallel Execution

Batch-process instances concurrently with configurable worker pools.

Method

How It Works

TK-Boost operates in two phases: offline knowledge discovery and online corrective augmentation.

1

Discover Misconceptions

Run the NL2SQL agent on a small set of labeled queries. Compare results to ground truth and identify recurring mistakes—columns misused, joins misunderstood, filters misapplied.

2

Generate Tribal Knowledge

For each misconception, generate a reusable natural-language corrective statement paired with applicability conditions (SQL keywords, tables, columns, data types) that define when it should be used.

3

Index & Store

Index knowledge in TK-Store with structured tags so relevant rules can be retrieved precisely from any SQL draft.

4

Correct at Query Time

When answering new queries, the agent generates a SQL draft. TK-Boost retrieves matching knowledge and feeds targeted CTE-level feedback to fix misconceptions before producing the final answer.

terminal 
# Clone and install
git clone https://github.com/abiswal2001/TK-Boost.git
cd TK-Boost
pip install -r requirements.txt

# Run the SQL agent on a single instance

  --instance-id local066 \
  --jsonl-path data/spider2-lite.jsonl \
  --model azure/gpt-4.1 \
  --out-base outputs/baseline

# Run with CTE refinement
python src/agents/sql_agent_runner.py \
  --instance-id local066 \
  --jsonl-path data/spider2-lite.jsonl \
  --model azure/gpt-4.1 \
  --validate-cte \
  --out-base outputs/validated

CTE Refiner (Validation)

The CTE refiner iteratively checks and improves each CTE in the final SQL, then refines the final SELECT. Enable with --validate-cte:

python src/agents/sql_agent_runner.py \
  --instance-id local066 \
  --jsonl-path data/spider2-lite.jsonl \
  --model azure/gpt-4.1 \
  -c data/contexts/predicted_cte_briefs_local.csv \
  -t data/contexts/predicted_tablescols_local.csv \
  --validate-cte \
  --out-base outputs/local_validated \
  --verbose

What happens:

  1. Agent generates initial SQL solution
  2. SQL is parsed into CTEs and final SELECT
  3. Each CTE is validated individually (max 25 turns per CTE)
  4. If issues are found, refiner suggests fixes and agent revises
  5. Final SELECT is validated with all CTEs in place
  6. Validated SQL and results are saved
Validation Output Files

When validation is enabled, these files are created per instance:

outputs/local066_20251031_120000/
├── execution_query.sql              # Original agent SQL
├── execution_result.csv             # Original agent results
├── execution_query_validated.sql    # SQL after validation
├── execution_result_validated.csv   # Results after validation
├── refiner_cte1.json                # Refiner verdict for first CTE
├── refiner_cte1_trace.txt           # Refinement trace for first CTE
├── refiner_cte2.json                # Refiner verdict for second CTE
├── refiner_cte2_trace.txt           # Refinement trace for second CTE
├── refiner_final_select.json        # Refiner verdict for final SELECT
├── refiner_final_select_trace.txt   # Refinement trace for final SELECT
├── messages.json                    # Full conversation history
├── processed_trace.txt              # Human-readable trace
├── gt_query.sql                     # Ground truth SQL
├── gt_result.csv                    # Ground truth results
└── gt_result.json                   # Ground truth results (JSON)
Validation-Only Mode (From Existing Outputs)

Run the refiner on existing SQL outputs without regenerating agent responses using --validate-output:

python src/agents/sql_agent_runner.py \
  --validate-output outputs/snowflake_norefiner \
  --jsonl-path data/spider2-lite.jsonl \
  --model azure/gpt-4.1 \
  -c data/contexts/predicted_cte_briefs_snowflake_azure_o3.csv \
  -t data/contexts/predicted_tablescols_snowflake_azure_o3.csv \
  --verbose

Use cases:

  • You ran the agent without validation and want to add validation later
  • You want to re-run validation with different settings (e.g., different model)
  • You want to validate a subset of outputs without re-generating them

Troubleshooting

Snowflake Connection Issues:

  • Verify credentials in ~/.snowflake/config
  • Check network connectivity to Snowflake
  • Ensure warehouse is running

BigQuery Permission Errors:

  • Run gcloud auth application-default login
  • Verify service account has BigQuery permissions
  • Check project ID in credentials

LLM Rate Limits:

  • Reduce --workers in parallel runner
  • Add retry logic with exponential backoff
  • Use a different model tier

Empty Validation Results:

  • Check that execution_query.sql exists in output directories
  • Verify instance IDs match between JSONL and output directories
  • Ensure predicted hints CSVs contain the instances you're validating
